# План: telemux как control-plane флота MTProxy

Основа - [ADR 0001](adr/0001-pull-reconcile.md): мастер на машине с PostgreSQL primary, агенты на
машинах забирают желаемое состояние по HTTP long-poll, релеи - через туннели своих машин-выходов.
Смена мастера - [ADR 0002](adr/0002-master-failover.md): Patroni + etcd на трёх машинах управления,
роль telemux производна от роли локального PG, поверх - кворумный fencing в telemux и `/api/leader`.

Правило разработки: **тесты вперёд**. Каждый шаг ниже начинается с теста, который падает на текущем
коде, потом код, потом тест зеленеет. Шаг не готов без теста и документации.

## 1. Кто чем владеет

Подписка не привязана к серверу: один и тот же набор пользователей действует на всех машинах,
«сменить сервер» в боте - это выбрать другую ссылку. Поэтому граница проходит так.

| Остаётся в боте (бизнес) | Переходит в telemux (инфраструктура) |
|---|---|
| тарифы, оплаты, промокоды, рефералка, refund | доставка и применение конфигов telemt и mtg на все машины |
| покупка, продление, подарок, триал, block, delete | проверка «конфиг принят» и откат, учёт «желаемое / применённое» |
| выдача секрета и срока, смена ключа, напоминания | WEB-профили telemt (собираются на машине из списка пользователей) |
| экраны, /status, выбор ссылки, сборка строки `tg://` | здоровье машин, версии бинарей, канарейки, каналы обновления |
| уведомления пользователям (в том числе о квоте) | статистика с машин: подключения, квоты, число пользователей |
| | сверка дрейфа, журнал применений, «применить сейчас» |
| | реестр точек входа (хост, порт, домен, протокол, через релей или напрямую) |

Спорное, решаем по ходу:

- **Ключ пользователя в telemt.** Сейчас `<username>_<id>`: смена username пересоздаёт пользователя
  на всех машинах. Предложение - стабильный ключ по id подписки. Переход - отдельным шагом с
  миграцией ключей и проверкой, что старые ссылки работают (секрет не меняется, ключ - только имя).
- **Окно старого секрета после смены ключа.** Сейчас отдельная запись `<key>_legacy`. Предложение -
  у пользователя список `secrets: [{secret, expires_at}]`, рендер сам раскладывает.
- **Точки входа для ссылок.** Данные (`server_endpoints`, настройки mtg-нод, домены) - инфраструктура,
  их владельцем становится telemux и отдаёт боту по API. Строку ссылки собирает бот.

## 2. API

**Контракт - spec-first.** OpenAPI 3.1 yaml в репо - единственный источник правды. Бэкенд
генерируется `oapi-codegen` (strict-server под `net/http`), фронт - `openapi-typescript` + zod.
Страница `/api-docs` - swagger-ui по той же спеке. Тест контракта: каждая ручка из спеки
отвечает по схеме, лишних ручек нет.

Общие правила:

- все пути под `/api/v1`;
- списки - `limit` (1-100, по умолчанию 20) и `offset`, ответ `{data, paging: {total, limit, offset}}`,
  в `paging.limit` - фактически применённый;
- ошибки - `{code, message}`: 400 валидация, 401 не вошёл, 403 чужой токен, 404 нет объекта,
  409 запись на реплике / конфликт ревизии / guard массового удаления, 422 недопустимый переход
  раскатки, 503 - только недоступна база или мастер, 500 - баги; текст ошибки базы - в лог, клиенту
  не отдаётся;
- запись - только на мастере (409 на остальных);
- все сравнения токенов - постоянные по времени.

**Авторизация.** Люди - по сессии, сессии в базе (переживают смену мастера). Агенты - токен на
каждую машину, зашифрован в базе. Бот - отдельный токен с правами «писать ревизии пользователей,
читать статус применения и точки входа».

**Ресурсы.**

| Для кого | Ручки |
|---|---|
| агенты и мосты | `GET /v1/desired?target&rev` (long-poll), `POST /v1/observed` |
| бот | `PUT /api/v1/users` (полный набор, guard массового удаления), `PUT/DELETE /api/v1/users/{key}` (точечно: block, refund, смена ключа); ответ - номер ревизии |
| бот | `GET /api/v1/revisions/{rev}/status?wait=10s` - на скольких машинах применена (бот выдаёт ссылку после применения на нужных машинах) |
| бот | `GET /api/v1/endpoints` - точки входа с состоянием; `GET /api/v1/stats/connections`, `GET /api/v1/stats/quota` |
| бот и панель | `GET /api/v1/drift` - машины, где желаемое не совпадает с применённым дольше порога |
| панель | `targets`, `targets/{code}`, `pairs`, `apply-log`, `POST targets/{code}/apply`, `POST targets/{code}/retry` |
| панель | `artifacts`, `rollouts` (+ `/advance`, `/pause`, `/abort`), `channels` |
| панель | `users` (как сейчас, на новых правилах), `nodes/join-token` |

## 3. Панель

Стек: React 19 + Vite + TypeScript, antd, @tanstack/react-query, react-router, zod, i18next (ru/en),
вшивается в бинарь как сейчас. Обновления экрана - SSE от мастера с инвалидацией кэша.

Экраны. Лицензия telemux - GPL-3.0, поэтому код панели 3x-ui (тоже GPL-3.0) берём и адаптируем,
сохраняя в заимствованных файлах указание на источник:

1. **Пары** - главный экран. Релей, два его сервера, два выхода. По каждой машине: статус,
   ревизия желаемая и применённая, версия бинаря (с отметкой канарейки), «видели N секунд назад»,
   через какой мост, кнопки «применить сейчас» и «повторить». Раскрывающаяся строка - история и
   последние ошибки.
2. **Дрейф** - только расхождения дольше порога.
3. **Сборки и раскатки** - список сборок, создание раскатки по этапам, выдержка, критерии
   здоровья, пауза и остановка, срок канарейки и команда отката.
4. **Журнал применений** - фильтры по машине, ресурсу, статусу.
5. **Пользователи** - серверная пагинация, фильтры, продление «+N дней» пачкой, QR и ссылки.
6. **Машины** - реестр, токены агентов, join-token.
7. **Настройки** - каналы обновления, режим разработчика, тревоги.
8. **API** - swagger-ui.

## 4. Бинари, канарейки, режим разработчика

- **Сборки.** CI собирает telemt, mtg-multi и сам telemux из тегов наших форков; версия с
  суффиксом (`3.5.17+sess.1bdefc24`), sha256, адрес. Мастер хранит у себя копию бинаря и отдаёт её
  агентам (релеи получают через мост), без скачивания с GitHub на машинах.
- **Каналы.** У каждой машины канал: `stable` (наши релизы), `dev` (rolling-сборка из последнего
  коммита, как `dev-latest` в 3x-ui) или закреплённая версия. Переход на `dev` - только явным
  действием.
- **Режим разработчика** - настройка панели: показывает канал `dev`, позволяет назначить машине
  любую сборку, включает подробный журнал агента. Без него доступны только `stable` и раскатки.
- **Раскатка (канарейка).** Этапы «одна машина → пара → все», выдержка, критерии здоровья
  (рестарты, «конфиг принят», проба MTProto, метрики против исходной версии). Провал на любом
  этапе - остановка, агенты сами возвращаются на прежнюю версию.
- **Проверка обновления на машине.** Агент: скачать, сверить sha256 и `--version`, бэкап,
  атомарная замена, рестарт, проверка (процесс жив, рестарты не растут, порты слушаются, конфиг
  принят, нет panic). Не прошло - откат бинаря и отчёт `failed`.
- **Конфиг и версия связаны.** Ключи конфига, которых нет в старых версиях, включаются, только
  когда вся целевая группа уже на нужной версии.
- **Самообновление telemux** - тем же механизмом, с ручным аварийным путём.

## 5. Порядок работ

Каждый пункт - отдельный MR. Внутри пункта: тест → код → документация.

**Этап 0. Гигиена (telemux).** Готово.
- исправить найденное: сравнение Bearer не постоянное по времени; `paging.limit` не тот, что
  применён; `201` теряет `Content-Type`; `POST /api/sync` без проверки мастера; текст ошибки базы
  уходит клиенту; любая ошибка хранилища - 503;
- тесты на каждую из этих ошибок.

**Этап 1. Контракт и ревизии (telemux + бот).** Сторона telemux готова: спека `api/openapi.yaml`, миграция `0003_revisions.sql`, рендер `internal/telemtcfg/render.go`, API `/api/v1/users` и `/api/v1/revisions`. Осталось: бот переходит на `PUT /api/v1/users`, генерация типов в панели.
- OpenAPI-спека, генерация бэка и фронта, тест контракта;
- миграции: `targets`, `desired_config`, `observed_state`, `apply_log`;
- рендер `users.toml` перенести в telemux (`internal/telemtcfg`), детерминированный (без
  зависимости от текущего времени), тесты «одинаковые данные - одинаковый хеш»;
- бот: `PUT /api/v1/users` вместо push по SSH на машины (параллельно со старым синком, только
  запись ревизий); тесты на guard массового удаления и точечные изменения.

**Этап 2. Мастер и агент в режиме «только сравнить».** Готово: `/v1/desired` (long-poll), `/v1/observed`, токены машин (`0004_agent_tokens.sql`), агент `internal/agent` и команды `target`, `agent-token`, `publish`, `agent`.
- мастер: `GET /v1/desired` long-poll, `POST /v1/observed`, токены машин;
- агент: модуль telemt (сравнение файла на диске с желаемым, без записи), отчёт;
- тесты: долгий опрос отдаёт новую ревизию сразу; старая ревизия не применяется; машина после
  простоя получает последнее состояние; чужой токен - 403.

**Этап 3. Агент применяет (telemt).** Готово: режим `apply` (`internal/agent/apply.go`), WEB-профили (`internal/telemtcfg/webprofiles.go`), тесты на эмуляторе telemt.
- атомарная замена `users.toml` + WEB-профили одним шагом, SIGHUP, ожидание «принят», откат;
- тесты на эмуляторе telemt: принят; отвергнут - откат; нет места на диске; обрезанный файл;
  профиль на выбывшего пользователя.

**Этап 4. Мосты и релеи.**
- мост с кэшем на машине-выходе, пересылка отчётов;
- тесты: мастер недоступен - мост отдаёт кэш; два моста с разными ревизиями - релей берёт новую.

**Этап 5. Пилот ps2 + pr2** (прод, по команде): «только сравнить» сутки → применение →
выключение старого SSH-синка для пары → следующая пара.

**Этап 6. mtg** (модуль агента, конфиг mtg-сервера, релеи local-mtg); решение по 3x-ui.

**Этап 7. Бинари и канарейки** (`artifacts`, `rollouts`, каналы, режим разработчика, CI-сборки).

**Этап 8. Панель** - экраны по разделу 3, по мере готовности API (можно параллельно с этапами 2-7).

**Этап 9. Перенос из бота** - точки входа, статистика, квоты, дрейф; бот переходит на API telemux,
старый код синка удаляется.

## 6. Что можно делать параллельно

- **Сессия «бот»** (tg-bots): этап 1 со стороны бота - запись ревизий через API, детерминированный
  рендер, точечные изменения пользователей.
- **Сессия «панель»** (telemux, фронт): каркас панели, экраны 1-2 на заглушках по OpenAPI-спеке.
- **Здесь**: этапы 0-4 - бэкенд мастера и агента.
- Уже идут: telemt в 3x-ui. Смена мастера (ADR 0002) - код в telemux готов, дальше стенд и
  перевод кластера по плану из ADR.
