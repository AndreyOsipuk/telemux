# Спецификация: релей - через свою зарубежную ноду

- Версия: 0.5 (утверждена владельцем заочно 2026-11-20, разбор после; 0.3 - итоги R7, R8;
  0.4-0.5 - уточнения по итогам реализации и ревью, раздел 10)
- Дата: 2026-11-20
- Решение: [ADR 0009](../adr/0009-relay-via-exit.md)
- Затрагивает: telemux (мост, агент, мастер, API), бот (watchdog, аудит перед деплоем)

Спецификация - источник истины. Код и тесты пишутся по ней; каждый тест называет пункт
(`R3.2`), который проверяет. Изменение поведения - сначала правка спецификации и новая
версия, потом код.

## 1. Цель

Состояние релеев в РФ знает только telemux, и узнаёт его по цепочке
**мастер -> зарубежная нода -> релей**. Никто не ходит на релей снаружи. Живой релей не
может оказаться «мёртвым» оттого, что его не видно с какой-то зарубежной ноды.

## 2. Границы

Входит:
- мост выхода знает, какие релеи через него ходят, и отдаёт сводку;
- агент выхода шлёт сводку мастеру;
- мастер считает статус пар и релеев, поднимает и снимает тревоги;
- watchdog и аудит перед деплоем берут состояние релеев только из telemux;
- исследование: как telemt и mtg на релее ведут себя, когда путь до выхода не работает
  (R7), - отчёт и предложение, без изменения поведения.

Не входит (следующие версии):
- проверки изнутри РФ: выход релея в Telegram, TLS-эмуляция, мосты `relay_exits`, точки входа
  глазами клиента - локальные проверки агента релея;
- пересылка ленты событий в Telegram, если её ещё нет, - отдельная спецификация;
- перестройка туннелей на релеях (xray) - это работа с данными и машинами, раздел 8.

## 3. Термины

- **Выход (exit)** - зарубежная нода, машина telemux вида `exit`.
- **Релей** - машина в РФ, вида `relay`.
- **Своя нода релея** - выход, у которого `targets.relay_code` = код релея: через его мост
  релей ходит к мастеру, и через него же идёт трафик релея в Telegram (выходы релея в базе
  бота, `relay_exits`). Это не обязательно `node_code` серверов: нода сервера и выход
  трафика релея могут быть разными машинами.
- **Мост** - процесс `telemux bridge` на выходе; через него агент релея ходит к мастеру.
- **Пара** - релей и его свои ноды.
- **Порог тишины релея** `T_relay` = 3 мин. **Порог тишины машины** - существующий
  (`SilentAfter`, ADR 0007).

## 4. Требования

### R1. Мост знает свой релей

- **R1.1** Мост с заданным кодом выхода (`TELEMUX_BRIDGE_CODE`) ставит в каждый запрос к
  мастеру заголовок `X-Telemux-Bridge: <код>`. Без кода заголовок не ставится, мост работает
  как раньше.
- **R1.2** Мост запоминает для каждого релея, который через него ходит: время последнего
  запроса, число запросов, ответил ли мастер (`master_ok`), последнюю ошибку мастера. Код
  релея мост берёт только из ответа мастера на `/v1/desired` (поле `target`); запрос с
  токеном, которого мастер не признал, в сводку не попадает.
- **R1.3** Мастер недоступен: запрос релея всё равно учитывается (релей жив), `master_ok =
  false`, ошибка записана.
- **R1.4** `GET /v1/relays` на адресе моста (loopback) отдаёт сводку по контракту 5.1. В
  ответе нет токенов и их хешей.

### R2. Нода отвечает за свой релей

- **R2.1** Агент выхода с заданным `TELEMUX_AGENT_BRIDGE_URL` в каждом runtime-отчёте
  передаёт сводку своего моста (контракт 5.2).
- **R2.2** Мост не ответил за 3 с - в отчёте `bridge.error`, остальной отчёт уходит как обычно.
- **R2.3** Без `TELEMUX_AGENT_BRIDGE_URL` поле `bridge` в отчёте отсутствует.

### R3. Мастер считает статус пар

- **R3.1** Мастер записывает, через чей мост пришёл отчёт релея: `relay_via`, `relay_via_at`.
  Учитывается только код существующей машины вида `exit`; иной код игнорируется с WARN в
  логе, отчёт принимается.
- **R3.2** Статус каждой своей ноды релея (`relay_status` в паре):
  - `exit_down` - выход молчит дольше порога тишины машины;
  - `ok` - выход жив, и релей ходил через его мост не позже `T_relay` назад (по сводке моста
    или по `relay_via_at`);
  - `relay_silent` - выход жив, релей через его мост молчит дольше `T_relay`.
- **R3.3** Статус релея `down` - только если ни через одну свою ноду он не ходил дольше
  `T_relay` и его агент молчит. Пока хоть одна своя нода видит релей - он не `down`.
- **R3.4** `foreign_bridge = true` у релея, если его последний `relay_via` - выход не из его
  пары.
- **R3.5** Поля из R3.1-R3.4 отдаются в `GET /api/v1/pairs` и `GET /api/v1/machines`
  (контракт 5.3). Существующие поля и их смысл не меняются.

### R4. Тревоги

- **R4.1** Детектор ADR 0007 пишет в `machine_events` события только на переходе:
  - `relay_silent` (выход, релей) - пара перешла в `relay_silent`;
  - `relay_ok` (выход, релей) - пара вернулась в `ok`;
  - `foreign_bridge` (релей, выход) - релей пошёл через чужой мост;
  - `down`/`up` по релею - по правилу R3.3, а не только по тишине агента.
- **R4.2** Повторный проход детектора без изменений не создаёт событий.
- **R4.3** Пара с `exit_down` не создаёт `relay_silent`: о релее она ничего не утверждает.
- **R4.4** Выключенные машины (`enabled=false`) тревог не порождают (как в ADR 0007).

### R5. Пары берутся из туннелей

- **R5.1** Источник пар - только `targets.relay_code` выходов. Карта серверов
  (`servers.node_code`) на пары не влияет и с ними не сверяется: нода сервера и выход
  трафика релея - разные роли.
- **R5.2** Привязка выхода к несуществующему релею - 400 `unknown_machine` (как сейчас), не
  5xx.
- **R5.3** У релея без своих нод (`targets.relay_code` не указывает на него ни у одного
  выхода) статус пары `no_exit`, тревога `relay_no_exit` один раз на переходе.

### R6. Бот не ходит на релеи

- **R6.1** Релей «под telemux» - машина вида `relay` из `GET /api/v1/machines`, у которой есть
  агент (`seen_at` не пуст). Определяется в одном месте, раз за цикл проверок.
- **R6.2** Для релея под telemux watchdog не выполняет ни одного SSH- и TCP-обращения к
  релею и через релей (порт-чек, «второе мнение», диск, клиенты, конфиг, TLS-эмуляция,
  выход в Telegram, мосты выходов, точки входа, метрики, версия бинаря, smoke по SSH).
- **R6.3** Состояние такого релея watchdog берёт из telemux:
  - живость и статус пары - `pairs`, события `down`/`relay_silent`/`foreign_bridge`;
  - диск > 90% - `runtime.host.disk_pct`;
  - клиенты - `runtime.telemt`;
  - пользователи и конфиг применены - `observed`;
  - telemt принял конфиг - `telemt_api_ok` и `apply_failed`;
  - версия - `machines[].telemt_version`.
- **R6.4** Ранее открытые тревоги SSH- и TCP-проверок по релею под telemux закрываются.
- **R6.5** telemux недоступен - ни одной тревоги по релеям, одна тревога «telemux недоступен».
- **R6.6** Релей без агента telemux проверяется как раньше.
- **R6.7** Аудит перед деплоем для релеев под telemux не ходит по SSH. Он берёт из telemux
  пары, статусы (R3) и применённые ревизии и валит деплой только при `down`,
  `foreign_bridge` или `apply_failed`.

### R7. Релей не принимает клиентов, когда путь не работает (исследование)

- **R7.1** Выяснить и описать, что сейчас делают telemt и mtg-multi на релее, когда выход
  (мост в Telegram через свою ноду) недоступен: принимают ли соединение, держат ли его,
  что видит клиент, есть ли в них проверка апстрима, отключение листенера, health-check.
- **R7.2** Предложить способ, при котором клиент не застревает на мёртвом пути (telemt и
  mtg не принимают соединения или сразу закрывают их), и как это включить через telemux.
- **R7.3** Результат - отдельный раздел в этой спецификации (версия 0.3) и пункт плана.
  Поведение прокси в этой версии не меняется.

#### Результат исследования R7 (2026-11-20)

- **Почему релей принимает клиентов на мёртвом пути.** Исходящие соединения telemt и mtg
  на релее заворачиваются iptables (REDIRECT, цепочки `TG_TELEMT`, `TG_MTG`) на локальный
  xray (`xray-relay`, балансиры `bal-telemt`, `bal-mtg`), а он уже ведёт в выход. Поэтому
  `connect()` к Telegram успешен всегда, даже когда туннель мёртв:
  - health-check апстримов telemt (TCP к DC) всегда «здоров»;
  - mtg-multi пишет рукопожатие, не дожидаясь ответа.

  Клиент проходит FakeTLS и висит до таймаута.
- **Встроенных средств нет.**
  - Ворота приёма в telemt (`admission`) работают только с middle proxy, у нас
    `use_middle_proxy=false`.
  - В mtg-multi ворот нет, настоящая проба DC есть только в `doctor`.
  - Выключить листенер через API telemt нельзя.
- **Решение (следующая версия, R9 в 0.4):** агент telemux на релее проверяет путь сам.
  - Проба та же, что у watchdog: HTTPS-запрос к адресу Telegram из cgroup telemt и
    отдельно из cgroup mtg, раз в 5-10 с.
  - После 3 провалов подряд агент закрывает приём новых соединений на портах этого
    сервиса: iptables `REJECT --reject-with tcp-reset` для `ctstate NEW`, для 443 - на
    `lo:8443` за nginx.
  - После 2-3 успехов подряд приём открывается.
  - Страховки: предельное время закрытия; открыть, если сломалась сама проба.
  - Идущие соединения не рвутся. Клиент получает мгновенный отказ и уходит на следующий
    прокси.
  - Событие `path_down`/`path_up` уходит мастеру через мост.
  - Позже, по необходимости: такие же ворота внутри форков telemt и mtg-multi.

### R8. Пороги (исследование)

- **R8.1** Выяснить, как устроены пороги и тревоги о нодах в 3x-ui. Пороги этой версии
  (`T_relay` = 3 мин, тревога на переходе) остаются до решения.

#### Результат исследования R8 (2026-11-20)

- **Как в 3x-ui:**
  - heartbeat нод раз в 5 с, один провал - уже offline, событие только на переходе;
  - outbound - 3 провала подряд, причём считаются только новые пробы, а «восстановилось»
    уходит, только если до этого была тревога;
  - пауза 1 мин на пару (тип, источник);
  - массовые переходы сворачиваются в одно сообщение;
  - гистерезиса и напоминаний нет.
- **Берём в telemux:**
  - N провалов подряд по настоящим пробам;
  - тревога на переходе, «восстановилось» - только после тревоги;
  - пауза на пару (тип, источник);
  - массовые переходы - одним сообщением.
- **Добавляем сверх 3x-ui:**
  - гистерезис для нагрузки;
  - напоминание раз в 1-2 ч, пока проблема не ушла.
- Пороги этой версии не меняются. Правила выше - в следующей версии вместе с R9.

## 5. Контракты

### 5.1 `GET /v1/relays` (мост, loopback)

```json
{
  "bridge": "ps2",
  "relays": [
    {"code": "pr2", "last_seen": "2026-11-20T10:00:00Z", "requests": 1240,
     "master_ok": true, "last_error": ""}
  ]
}
```

`relays` отсортирован по `code`; пустой мост - `[]`.

### 5.2 runtime-отчёт выхода: поле `bridge`

```json
{"bridge": {"code": "ps2", "relays": [ ...как в 5.1... ], "error": ""}}
```

Хранится в `agent_runtime.bridge` (jsonb).

### 5.3 API мастера (только добавления)

- `Machine`: `relay_via` (string|null), `relay_via_at` (date-time|null), `foreign_bridge`
  (bool, только у релея).
- `PairMachine` (выход в паре): `relay_status`: `ok` | `relay_silent` | `exit_down`,
  `relay_last_seen` (date-time|null).
- `Pair`: `relay_down` (bool), `foreign_bridge` (bool).
- `MachineEvent.kind`: добавляются `relay_silent`, `relay_ok`, `foreign_bridge`,
  `relay_no_exit`; у события пары заполнены `code` (релей) и `exit` (выход).

### 5.4 Хранилище

Миграция `0014_relay_via.sql` (идемпотентная): `agent_state.relay_via`, `relay_via_at`;
`agent_runtime.bridge`; таблица состояния пар для детектора `pair_alert_state(relay, exit,
status, changed_at)`.

### 5.5 Конфигурация

- `TELEMUX_BRIDGE_CODE` - код выхода для моста.
- `TELEMUX_AGENT_BRIDGE_URL` - адрес моста для агента выхода
  (обычно `http://127.0.0.1:18480`).

## 6. Нефункциональные требования

- **N1** Обратная совместимость: старый мост, старый агент и старые клиенты API работают;
  новые поля только добавляются.
- **N2** Ошибки ввода - 4xx, 5xx - только отказ инфраструктуры; каждый 5xx в логе с
  причиной.
- **N3** Списки в новых местах API - с пагинацией, как остальные (`limit`/`offset`, `total`).
- **N4** Ни токенов, ни секретов, ни адресов машин в публичной документации и тестах репо.

## 7. Приёмка

Версия считается сделанной, когда:
- **A1** На каждый пункт R есть тест с его номером в названии; все тесты зелёные:
  - `go test ./...` с интеграционными тестами на PG;
  - тесты watchdog и shared;
  - `tsc`.
- **A2** Прошло ревью: review-core, review-go для telemux, review-js для бота.
- **A3** На проде после выкатки:
  - `GET /api/v1/pairs` показывает все пары `ok`;
  - у pr2 и pr3 `relay_down = false`;
  - за 30 мин watchdog не поднял ни одной тревоги «нет ответа» по релеям;
  - в логах watchdog и аудита нет SSH на релеи под telemux.
- **A4** Документация обновлена: README, `api/openapi.yaml`, `apps/watchdog/CLAUDE.md`.

## 8. Данные и выкатка

- **Порядок (уточнён в 0.4, U8):** мосты и агенты выходов и релеев -> мастер telemux ->
  бот. Новые мост и агент работают со старым мастером (N1); если первым выкатить мастер,
  все пары окажутся `relay_silent` и в ленту уйдут массовые события. Бот переключается
  последним, когда в `pairs` видны статусы.
- **Данные.** Пары в telemux (`targets.relay_code`) повторяют выходы релеев в данных бота, но
  местами расходятся с фактическим трафиком (второй сервер на релее идёт через выход
  первого). После выкатки статусы пар покажут это сами; сведение данных и раскладка без
  дублей - этап 5 плана. Конкретная прод-топология - в приватной документации бота (U25).

## 9. Решения владельца (2026-11-20)

1. Своя нода каждого релея - выход, через который идёт его трафик; у релея, где у сервера
   выход выведен, своя нода - машина, держащая его мост.
2. Выход трафика релея может быть машиной без своего сервера - это всё равно своя нода.
3. Одна своя нода у релея - допустимо: релей - только релей; упала нода - тревога по ноде и
   пути, а не по релею. Нужно, чтобы telemt и mtg на релее не принимали клиентов на мёртвом
   пути - R7.
4. Пороги оставить, изучить 3x-ui - R8.

## 10. Уточнения 0.4 (по итогам реализации)

Действуют поверх разделов 4-5. Обнаружены при реализации, решены минимально; тесты
ссылаются на эти пункты.

- **U1 (к R3.2).** Агент релея ходит к мастеру через первый доступный мост, и вторая своя
  нода его не видит - она навсегда была бы `relay_silent`. Поэтому агент с двумя и более
  адресами мастера раз в период runtime-отчёта делает `GET /v1/desired?wait=0s` через каждый
  адрес. Работает только после обновления агентов релеев.
- **U2 (к R1.2).** Ответ мастера 304 на `/v1/desired` мастер даёт, только проверив токен и
  `target` запроса, поэтому мост принимает его как подтверждение кода релея: после
  перезапуска моста код известен с первого long-poll.
- **U3 (к 5.3).** `Pair.status`: `ok` | `down` | `no_exit` - поле для R3.3 и R5.3.
- **U4 (к 5.3, 5.4).** В событиях существующее поле `machine` - это релей, новое поле `exit` -
  выход. Миграция 0014 добавляет `machine_events.exit` и расширяет CHECK по `kind`.
- **U5 (к R4).** По релею без агента события пар не создаются (как в ADR 0007), статус пары
  в API считается.
- **U6 (к 5.1).** `last_error` - последняя ошибка мастера, после успеха не сбрасывается.
  Текущее состояние показывает `master_ok`.
- **U7 (к R5.2).** `POST /api/v1/targets` с несуществующим релеем отдаёт `unknown_machine`
  (раньше `bad_request`).
- **U8 (к разделу 8).** Порядок выкатки: мосты и агенты, затем мастер, затем бот.
- **U9 (к R6.3).** Watchdog берёт состояние из `pairs` и `machines`, а переходы считает сам.
  Ленту событий в этой версии он не читает.
- **U10 (к R6.5).** Пока telemux недоступен, релеи из последнего удачного списка не
  проверяются, а релеи без агента проверяются как раньше. Если списка ещё нет (watchdog
  перезапущен при лежащем telemux), не трогается ни один релей.
- **U11 (к R6.7).** telemux недоступен - аудит валит деплой (FAIL), а не пропускает релеи
  вслепую. Обход - переменная `AUDIT_TELEMUX_OPTIONAL=1`: WARN вместо FAIL. Она нужна, чтобы
  выкатить исправление при лежащем telemux.
- **U12 (к R6.3).** Клиенты берутся из `machines[].connections` при `telemt_api_ok = true`, без
  отдельного запроса runtime по каждой машине.
- **U13 (к R6.1, R6.2).** Релей бота сопоставляется с машиной telemux по адресу:
  `servers.public_ip` бота = `address` машины в telemux. По коду - только если адреса в ответе
  нет. Расхождение (адрес есть в одном месте и нет в другом, или код совпал, а адрес нет) -
  WARN с перечнем; такой релей не считается под telemux. В аудите управляемыми считаются
  все пары с одним `RELAY_IP`, если управляема хоть одна.
- **U13a (к 5.3).** `Machine.address` (string|null) - адрес машины из `settings.address`, для
  сопоставления по U13.
- **U14 (к R6.3).** Если на машине нет ресурса `telemt.users`, сверка пользователей не
  «совпадает», а `mismatch` с причиной «ресурс не назначен в telemux».
- **U15 (к R6.4).** Карточки `relay:`, `relaypath:`, `relaybridge:` закрываются, когда релей
  выключен, пропал из telemux, потерял агента или telemux не настроен - в том числе после
  перезапуска watchdog (поиск по базе).
- **U16 (к R6.7).** Аудит telemux не смог отработать (нет bun, ошибка запуска, нет файла
  результата) при настроенном telemux - FAIL с причиной; при `AUDIT_TELEMUX_OPTIONAL=1` -
  WARN, и пары под telemux по SSH всё равно не проверяются.
- **U17 (к U1).** Проба своих нод - отдельный тикер агента релея (не реже раза в 60 с), не
  зависит от runtime-цикла и его паузы при `ErrRuntimeUnsupported`; адреса опрашиваются
  параллельно с таймаутом 5 с; мёртвый адрес не задерживает остальные.
- **U18 (к R3.1).** `relay_via` пишется только машинам вида `relay`.
- **U19 (к R4.1).** Пока релей `down` (R3.3), события пар `relay_silent`/`relay_ok` по нему не
  создаются - одно падение даёт одно событие `down`.
- **U20 (к R3.2, R3.3, R4.4).** Выключенный выход не участвует в статусах пар и в расчёте
  `down` релея.
- **U21 (к R3.2).** Сводка моста учитывается, только если runtime-отчёт выхода свежий (не
  старше порога тишины машины) и код сводки совпадает с кодом выхода.
- **U22 (к R3.2-R3.5).** Статусы в API и детекторе считаются от одного времени - `now()`
  базы.
- **U23 (к R1.2).** Мост забывает релей, который не ходил через него 24 ч.
- **U24 (к 5.1).** `last_error` - класс ошибки без адресов и query.
- **U25 (к N4).** Прод-топология (какой сервер через какой релей и выход идёт, имена
  машин) в публичный репо не попадает - она в приватной документации бота.
