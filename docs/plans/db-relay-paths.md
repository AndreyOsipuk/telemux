# Пути агента релея из БД

Администратор на мастере редактирует включённые цели-выходы и их привязки.
Для включения через API отправить `PUT /api/v1/targets/{код-релея}`
с телом `{"settings":{"relay_paths_managed":"1"}}` в админской сессии.
На целевом релее настройка `relay_paths_managed=1` включает выдачу списка.
Значение `0` приостанавливает раздачу обновлений. Агент при этом сохраняет
последний принятый список. Для восстановления доступна локальная конфигурация
запуска и последняя проверенная копия.

    targets → мастер → доверенный мост → агент релея
                                            ↓
                  проверка кода нового моста и доступа к мастеру
                                            ↓
                  принять целиком и сохранить → проверять пути

При обычном опросе агент передаёт `X-Telemux-Accept-Relay-Masters: 1`.
На 200 и 304 мастер возвращает `X-Telemux-Relay-Masters` в raw Base64URL.
В JSON поле `paths` содержит объекты `exit` / `master`. Отсутствие заголовка
оставляет предыдущую настройку. Пустой список останавливает пробы; агент
сохраняет возможность опроса мастера. Мост передаёт настройки только из
свежего ответа мастера. Список содержит не более 16 путей и выдаётся только
агенту включённого релея. Ошибку реестра журналируем, синк конфигураций
продолжается с последним рабочим списком.

Мосты разворачиваются первыми, затем мастер и агенты. Для агентов сверить,
что активный юнит systemd создаёт `StateDirectory=telemux-agent` с режимом
`0700` и может записать кэш `/var/lib/telemux-agent/relay-paths.json`. Включать по одному
релею после проверки, что каждый путь отвечает кодом своего выхода.
Проверить отсутствие новых тревог, применение изменений из БД и старт
агента с сохранённой настройкой при недоступности мастера.
