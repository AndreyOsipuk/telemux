# ADR 0001. Доставка конфигов и версий: машина сама забирает желаемое состояние

- Статус: предложено
- Дата: 2026-11-18
- Заменяет: исходную модель telemux «PostgreSQL-реплика + telemux на каждой ноде, запись в telemt через API»

## Контекст

Флот прокси устроен парами «сервер за рубежом - релей в РФ»:

- **Серверы.** Восемь штук: четыре на telemt, четыре на mtg-multi. У каждого сервера своя
  зарубежная машина-выход (`psN`). Машина-выход держит обратный туннель VLESS к своему релею, через
  него уходит трафик к Telegram.
- **Релеи** (в РФ), четыре штуки. Каждый релей `prN` обслуживает два сервера: telemt-сервер `N` и
  mtg-сервер `N+4`. На релее работают telemt (общий для всех релеев список пользователей + свои
  WEB-профили) и mtg-multi (конфиг своего mtg-сервера). Прямого доступа к базе и к зарубежным
  машинам у релея нет: наружу он ходит только по туннелям, которые держат его машины-выходы.
- **Управление.** Бот продаж и PostgreSQL (primary + реплики) живут на части зарубежных машин.

Сейчас конфиги раскладывает бот: по событию (оплата, продление, подарок) он сам ходит на каждую
машину по SSH и кладёт файл. Повторы - через 5 и 60 секунд, дальше только тревога. Машина,
недоступная в момент события, остаётся на старом списке до следующего события или суточной
чистки, и новые или продлённые пользователи на ней не подключаются. Отдельные механизмы синка у
telemt, mtg и 3x-ui, состояние повторов живёт в памяти процесса бота, версии бинарей
раскатываются руками с ноутбука, канарейки - соглашение, а не механизм.

Исходная модель telemux (PG-реплика на каждой машине, telemux пишет в telemt через machine-API)
для релеев не подходит:

- на релей уехала бы вся база (платежи, контакты пользователей) - а релей наименее защищённая машина;
- поток репликации и Patroni через ТСПУ хрупки и тяжелы;
- запись пользователей через API telemt конфликтует с `include = users.toml` (дубль `[access.users]`
  ломает конфиг), WEB-профили API не поддерживает, а секрет в `GET /v1/users` не виден - его смена
  не попадает в diff.

## Решение

**Уровневая сверка (level-triggered reconcile) с доставкой по HTTP long-poll, один мастер, релеи -
через туннели своих машин-выходов.**

Машина не ждёт, пока ей что-то пришлют, а сама держит запрос «моя ревизия N, есть новее?». Сервер
отвечает сразу, как только появилась новая ревизия, иначе через ~60 с пустым ответом, и агент
спрашивает снова. Машина, пролежавшая сколько угодно, при первом же соединении получает
**последнее** состояние целиком - отдельного механизма догона нет, он встроен в модель.

```
                     ┌──────────────────────────────────────┐
                     │ мастер telemux                       │
                     │ на машине с PostgreSQL primary       │
                     │ (бот пишет ревизии, панель, API)     │
                     └──────────────────┬───────────────────┘
                 бандлы (long-poll, HTTPS + токен машины)
        ┌───────────┬───────────┬───────┴───┬───────────┬─────── ... ps1..ps8
        ▼           ▼           ▼           ▼           ▼
      ps1         ps5         ps2         ps6          ...      машины-выходы:
   (выход С1)  (выход С5)  (выход С2)  (выход С6)                агент + мост с кэшем
        │ туннель   │ туннель   │           │
        └─────┬─────┘           └─────┬─────┘
              ▼                       ▼
             pr1                     pr2          ...  релеи: агент (telemt + mtg)
          (С1 + С5)               (С2 + С6)
```

### Роли

1. **Мастер.** Один `telemux` в роли мастера на той машине, где сейчас PostgreSQL primary. Роль
   определяется по самой базе (`pg_is_in_recovery()`): primary переехал - мастер переехал вместе с
   ним, отдельных выборов нет, split-brain невозможен. На мастере всё, что пишет:
   - бот (владеет бизнес-логикой: кто активен, сроки, ключи) пишет ревизии желаемого состояния -
     при любом изменении и раз в N минут; тексты файлов готовит существующим кодом бота; если хеш
     не изменился, новая ревизия не создаётся;
   - контроллер раскаток (какая версия бинаря положена машине на текущем этапе канарейки);
   - API и веб-панель;
   - приём отчётов агентов.
2. **Машина-выход** (`psN`). Агент применяет то, что положено самой машине (telemt, mtg, бинари,
   если они на ней есть; у части выходов это только туннель). Плюс **мост с кэшем**: берёт у мастера
   бандл своего релея, хранит последний и отдаёт его агенту релея внутрь туннеля. Если мастер
   временно недоступен, мост отдаёт бандл из кэша.
3. **Релей** (`prN`). Агент применяет бандл telemt (общий список пользователей + свои WEB-профили)
   и бандл mtg своего mtg-сервера. Обращается только к своим мостам через туннели.

Реплики PostgreSQL на других машинах нужны для переезда primary (и мастера вместе с ним), агенты
их не читают. Раздача с реплик (edge на каждой машине с репликой) не нужна в первой версии: когда
мастер недоступен, бот всё равно не может записать оплату, нового состояния нет, а последнего
бандла в кэше мостов хватает. Её можно добавить позже, если какой-то мост перестанет видеть мастера.

### Почему не другие варианты

| Вариант | Почему нет |
|---|---|
| PG-реплика на каждой машине | Вся база на релеях; репликация через ТСПУ; Patroni/etcd в РФ. Репликация остаётся только между машинами управления, где она уже есть. |
| Брокер сообщений (RabbitMQ, Kafka, NATS) | Брокер доставляет **события**, а нужно **состояние**: пропущенное событие - ровно текущая проблема, пришлось бы строить снимки поверх. Ещё один кластер с HA, долгие соединения через ТСПУ. Для ~12 машин и килобайтов данных избыточно. |
| Push по SSH (как сейчас) | Недоступна в момент события - отстала. SSH через ТСПУ - лотерея; ключ бота на каждой машине. |
| Мост толкает обновления в релей (push внутри туннеля) | Мосту снова пришлось бы помнить, кому что недоставлено, и повторять. Pull внутри того же туннеля этого не требует. |
| gRPC-стрим / WebSocket | То же, что long-poll, но сложнее в отладке и чувствительнее к обрывам долгих соединений. Выигрыша нет. |

## Модель данных (PostgreSQL, пишется только на primary)

```sql
-- Машины флота и их роль.
targets (
  code        text primary key,      -- ps1..ps8, pr1..pr4
  kind        text not null,         -- exit | relay
  relay_code  text,                  -- для выхода: релей, к которому он держит туннель
  enabled     boolean not null default true
)

-- Желаемое состояние: по одной строке на (машина, тип ресурса) и ревизию.
desired_config (
  target      text not null references targets(code),
  resource    text not null,         -- telemt.users | telemt.web_users | mtg.config | binary.telemt | ...
  revision    bigint not null,       -- глобальная монотонная (sequence)
  sha256      text not null,
  content     bytea,                 -- текст файла; для бинаря - null
  artifact_id bigint,                -- для binary.* - ссылка на artifacts
  created_at  timestamptz not null default now(),
  primary key (target, resource, revision)
)

-- Что машина реально применила (одна строка на машину и ресурс, перезаписывается).
observed_state (
  target      text not null,
  resource    text not null,
  revision    bigint,                -- применённая ревизия
  sha256      text,                  -- хеш на диске / из /stats
  status      text not null,         -- applied | failed | pending
  error       text,
  agent_version text,
  via         text,                  -- через какой мост пришёл отчёт (для релеев)
  seen_at     timestamptz not null,
  primary key (target, resource)
)

-- Собранные бинари.
artifacts (
  id bigserial primary key,
  name text, version text,           -- 3.5.17+sess.1bdefc24
  sha256 text, url text, git_commit text,
  min_config jsonb                   -- ключи конфига, которых нет в старых версиях
)

-- Раскатки (канарейки).
rollouts (
  id bigserial primary key,
  artifact_id bigint, baseline_artifact_id bigint,
  stages jsonb,                      -- [{"targets":["pr2"]},{"percent":25},{"all":true}]
  current_stage int, soak interval,
  health jsonb,                      -- критерии: рестарты, config/state, smoke, метрики
  status text                        -- running | paused | aborted | done
)
```

Ревизия монотонная: агент никогда не применяет ревизию меньше уже применённой. Так устаревший кэш
одного из мостов не откатит релей назад, если второй мост отдал более новую.

## Контракт

Один и тот же HTTP-контракт у мастера и у моста (мост - прокси с кэшем к мастеру):

```
GET  /v1/desired?target=<code>&rev=<N>     long-poll до 60 с
     Authorization: Bearer <токен машины>
     200 -> {"revision": M, "resources": [{"resource","sha256","content_b64"|"artifact":{url,sha256,version}}]}
     304 -> новее нет (истёк таймаут)

POST /v1/observed                          отчёт агента
     {"target", "agent_version", "resources": [{"resource","revision","sha256","status","error"}]}
```

- Токен машины даёт доступ **только к её** бандлу. Мост знает токен своего релея только как
  проводник: отдаёт бандл релея и пересылает его отчёты, своего доступа к чужим бандлам у него нет.
  Релей не видит чужих конфигов, базы и ключей.
- Мастер узнаёт о новых ревизиях от бота через `LISTEN/NOTIFY` на primary (с периодической
  проверкой на случай пропуска).
- Мост держит к мастеру собственный long-poll за бандл своего релея, поэтому новая ревизия
  оказывается в кэше моста за секунды, ещё до запроса релея.
- `observed` релея мост пересылает мастеру; если мастер недоступен - держит последний отчёт и
  досылает. Отчёты не критичны для работы машин.

## Алгоритм агента

1. Список адресов из конфига агента. У релея - **только через туннели**: оба его моста (выход
   telemt-сервера и выход mtg-сервера), WG - запасной туннель; прямого обращения к публичному
   адресу за рубежом у релея нет. У машины-выхода - адрес мастера (HTTPS с токеном) по фактически
   проверенным путям (см. «Сеть»).
2. Long-poll. Получил ревизию M > применённой - для каждого ресурса со своим модулем применения:
   - **telemt.users**: проверка места на диске; запись во временный файл и сверка sha; WEB-профили
     собираются **на машине** из её собственного `telemt.toml` и пришедшего списка пользователей
     (оба файла одним шагом); атомарная замена; SIGHUP; ожидание `/v1/config/state` «принят» до
     ~12 с; при отказе - откат обоих файлов.
   - **mtg.config**: то же; SIGHUP, если менялся только `[secrets]`, иначе restart; сверка
     `secrets_sha256` из `/stats`; откат.
   - **binary.***: скачать (релею - с моста), сверить sha256 и `--version`; бэкап; атомарная
     замена; restart; health-gate (active, число рестартов не выросло, порты слушаются, нет
     panic/config error); при сбое - откат бинаря.
3. Отчёт `observed`. При ошибке агент остаётся на последнем рабочем состоянии и **не повторяет
   ту же ревизию в цикле** - ждёт следующую (или команду «повторить» из панели).
4. На каждом цикле сверяет хеш файлов на диске с применённым: ручная правка или откат `.bak`
   видны как дрейф и исправляются.

## Сеть

### Релеи - только через туннели своих машин-выходов

**Каждая пара «машина-выход - релей» доставляет обновления через свой туннель** - тот же обратный
туннель VLESS, который выход держит к релею для трафика Telegram (соединение инициирует зарубежная
сторона, на релее - портал reverse). Напрямую с релея на публичный адрес за рубежом HTTP не идёт:
такой путь режет ТСПУ и он светит управляющий трафик.

Агент релея обращается к локальному адресу; маршрутизация xray на релее отправляет его в
reverse-выход нужной пары, мост принимает запрос на своём loopback-порту. Внутри туннеля спрашивает
агент релея (pull), а не мост толкает (push): туннель и так поднимает зарубежная сторона, а pull
не требует от моста помнить, кому что недоставлено, - при любом восстановлении туннеля агент
первым же запросом получает актуальное состояние.

У каждого релея два моста (выход telemt-сервера и выход mtg-сервера) - два независимых пути
получаются без отдельных туннелей. WireGuard остаётся запасным туннелем.

Мосты и правила маршрутизации в туннелях ставятся **вручную** при подключении пары (как сейчас
ставятся сами туннели); агент ими не управляет. Агенту нужен только адрес моста в его конфиге.
Требования:

- в каждом мосту - отдельное правило маршрутизации для порта моста (только он, не весь трафик);
  через мост xray по умолчанию не пускает приватные адреса, поэтому loopback-порт моста нужно
  разрешить явно;
- список доступа к портам туннеля на релее - только через файл, который пересобирается при
  старте (ручные правки iptables теряются);
- аудит: у каждого релея есть живой путь до хотя бы одного моста (это же видно в панели по
  `seen_at` и `via`).

### Связность между зарубежными машинами не гарантирована

Зарубежные машины тоже могут не видеть друг друга (фильтры хостеров, блокировки по подсетям,
сбои маршрутов) - полносвязность не предполагается. От этого зависят доставка бандлов с мастера на
машины-выходы, пересылка `observed` и репликация PostgreSQL. Поэтому:

- **до внедрения** снять матрицу связности «каждая с каждой» по нужным портам (мастер, PG, SSH) и
  записать её; пути строить только по проверенным направлениям;
- там, где прямой связи нет, - тот же приём, что для релеев: туннель (VLESS/WG) через машину,
  которая видит обе стороны;
- матрицу перепроверять регулярно (аудит), а не один раз: связность меняется при смене IP и
  хостера.

## mtg-multi: напрямую и через панель 3x-ui

mtg-multi поддерживается двумя способами, выбор - на уровне машины.

- **Напрямую** (ресурс `mtg.config`): mtg-multi работает своим systemd-юнитом с
  `/etc/mtg-multi/config.toml`. Текст конфига каждой машины собирает бот (там домены,
  порты, маскировка) и публикует в telemux (`PUT /api/v1/targets/{code}/resources/mtg.config`).
  Агент применяет его как бот: временный файл со сверкой, бэкап, SIGHUP, если изменились
  только `[secrets]` (иначе рестарт), проверка `secrets_sha256` в `/stats` mtg, откат при
  сбое. Машина может вести и telemt, и mtg - один агент, один отчёт.
- **Через панель** (ресурс `xui.clients`, машина вида `panel`): MTProto-вход мастер-панели
  3x-ui с настройками `inbound_id`, `node_id`, `port`, `node_code`. На машине писать
  нечего - конфигом владеет панель, а до своей ноды её доводит сама 3x-ui (флаг
  `config_dirty`, сверка раз в 5 с). Бот публикует желаемых клиентов входа (JSON), мастер
  telemux приводит к ним вход через API мастер-панели: своих лишних (`mtpx-` и суффикс
  ноды) удаляет целиком, чужих только отвязывает, защита от массового удаления, после
  записи перечитывает и сверяет. Отставание - в базе (желаемая ревизия > применённой),
  перепроверка дрейфа раз в 5 минут; работает только мастер.

## Что берём из 3x-ui

В 3x-ui мастер-панель синхронизирует ноды push-ом по HTTPS API ноды. Направление для нас не
принципиально: внутри поднятого туннеля одинаково работает и push, и pull. Мы выбираем pull, потому
что так «кто что недополучил» не нужно хранить на стороне отправителя. Остальные приёмы 3x-ui
переносим:

1. **Долговечный признак отставания.** В 3x-ui это флаг `config_dirty` + `config_dirty_at` в
   строке ноды: ставится при любой правке, касающейся ноды, переживает перезапуск мастера, снимается
   только после полностью успешной сверки и только если с тех пор не было новой правки (сравнение
   `config_dirty_at`). У нас то же самое выражено ревизиями: машина отстала, пока
   `desired.revision > observed.revision`. Признак живёт в базе, а не в памяти процесса.
2. **Частая сверка вместо разовой доставки.** В 3x-ui задача раз в 5 с сверяет каждую отставшую
   ноду, пока та не догонит. У нас то же делает long-poll агента и периодическая сверка хеша на
   диске (пункт 4 алгоритма агента).
3. **Отправлять только изменённое, удалять только своё.** В 3x-ui мастер хранит отпечаток последнего
   успешно отправленного содержимого каждого входа и пропускает неизменённые; лишнее на ноде удаляет
   только после того, как «принял» её существующие настройки при подключении, и только в пределах
   управляемого набора. У нас: ресурс применяется, только если его sha отличается от применённого;
   удаление - только того, что агент сам когда-то положил; новая машина сначала работает в режиме
   «только сравнить».
4. **Ошибка одного ресурса не блокирует остальные.** В 3x-ui ошибки сверки копятся
   (`errors.Join`), а сверка продолжается. У агента - так же: отказ telemt не мешает применить mtg,
   и в `observed_state` статус у каждого ресурса свой.
5. **Опрос живости со схлопыванием тревог.** В 3x-ui heartbeat раз в 5 с, события «нода упала /
   поднялась» уходят в Telegram, а массовое падение сворачивается в одно сообщение. У нас живость
   машины - это `observed_state.seen_at`; тревоги - по переходам, со схлопыванием.
6. **Очередь разовых команд.** В 3x-ui разовые действия (сброс трафика) копятся в таблице-очереди и
   доставляются при следующем контакте с нодой. У нас так доставляются «применить сейчас»,
   «повторить», «перезапустить» из панели: команда - ещё один ресурс бандла с ревизией.
7. **Токены машин.** В 3x-ui токен каждой ноды хранится в базе зашифрованным (AES-GCM, версия
   ключа), есть закрепление сертификата и mTLS. У нас так же хранятся токены агентов на мастере;
   агенты на машинах-выходах закрепляют сертификат мастера.

## Канарейки собственных сборок

- Сборка - CI из тега форка, версия с суффиксом (`3.5.17+sess.1bdefc24`), sha256 и url
  в `artifacts`. Для релеев бинарь отдаёт мост (кэширует у себя), чтобы не тянуть его через рубеж.
- Желаемая версия машины = baseline + активный этап раскатки. Контроллер на мастере переводит
  этапы после выдержки, если критерии здоровья выполнены на всех машинах этапа; при провале -
  `aborted`, и агенты сами возвращаются на baseline.
- Ключи конфига, которых нет в старых версиях (`min_config`), включаются только когда **все**
  целевые машины уже на нужной версии: иначе `config_strict` уронит старый бинарь.

## API и веб-панель

Панель telemux (React, уже вшита в бинарь) работает на мастере и становится панелью флота:

- пары «релей - два сервера - два выхода»: желаемое и применённое (ревизия, версия, статус, когда
  видели последний раз, через какой мост);
- кнопки «применить сейчас» и «повторить» для машины;
- сборки и раскатки: создать, следующий этап, пауза, стоп;
- журнал применений.

Люди входят по сессии, агенты - по своим токенам. Запись - только на мастере.

## Последствия

- Бот больше не ходит на машины по SSH для синка; уходят повторы, очереди в памяти, промежуточные
  хосты и гонки между экземплярами бота.
- Задержка после оплаты: запись -> NOTIFY мастеру -> ответ long-poll мосту -> ответ long-poll
  агенту релея -> применение. Итого несколько секунд. Бот может дождаться `observed` перед выдачей
  ссылки.
- Дрейф - одна таблица: `desired != observed` по каждой машине и ресурсу.
- Мастер - единственная точка записи. Пока он недоступен, машины работают на последнем состоянии,
  изменений нет (как и сейчас: без primary бот не принимает оплату).
- Новая зависимость - агент на каждой машине; его самого обновляет тот же механизм раскаток
  (с ручным аварийным путём).
- 3x-ui: mtg внутри панели в модель «файл машины» не ложится. Варианты - вывести mtg из 3x-ui под
  свой юнит (предпочтительно) или подавать секреты в процесс mtg локально в обход панели.
- Коды машин должны совпадать с ролями (`psN` = выход сервера N). Где сейчас не совпадают -
  переименовать до внедрения, в одном окне и по чек-листу (коды зашиты в конфиги, мониторинг, DNS).

## План перехода

0. Матрица связности: зарубежные машины между собой и с мастером, релеи через туннели до своих
   мостов. Выровнять коды машин с ролями.
1. Таблицы `targets`, `desired_config`, `observed_state`; бот пишет ревизии (параллельно со старым
   синком, ничего не ломая).
2. Мастер telemux на машине с primary + агенты на машинах-выходах в режиме «только сравнить»,
   затем с применением.
3. Мосты на машинах-выходах + правила маршрутизации в туннелях; агент на одном релее в режиме
   «только сравнить», затем с применением; затем остальные релеи. Старый SSH-синк релеев
   выключается последним.
4. mtg-серверы и mtg на релеях; решение по 3x-ui.
5. `artifacts` + `rollouts`, сборка в CI, канарейки через агентов.
6. Панель флота.
7. Конфигурация ОС (тюнинг, фаервол, защита от флуда) - как ещё один тип ресурса агента.
