# ADR 0008. Обновление telemt и mtg-multi кнопкой (ресурс stack)

- Статус: принято
- Дата: 2026-11-19
- Связано: [ADR 0007](0007-machines-ops.md) - раздел «Отложено», [план стека машины](../plans/machine-stack.md) - ресурс `stack`

## Контекст

Версии telemt и mtg-multi агент уже присылает в runtime-отчёте. Обновляют бинари руками: копируют
файл на машину и перезапускают сервис. Владелец решил брать новые версии из релизов GitHub.

Особенность флота: на релеях работает своя сборка mtg-multi (`1.15.0-webalias` - апстрим плюс
правка, ещё не влитая в апстрим). Обновление «на последний релиз апстрима» молча убрало бы эту
правку.

## Решение

### Источники

| Продукт | Репозиторий по умолчанию | Файл релиза | Контрольная сумма |
|---|---|---|---|
| telemt | `telemt/telemt` | `telemt-x86_64-linux-musl.tar.gz` (arm64 - `telemt-aarch64-linux-musl.tar.gz`) | `<файл>.sha256` |
| mtg | `dolonet/mtg-multi` | `mtg-multi-<версия>-linux-<arch>.tar.gz` | `mtg-multi-<версия>-checksums.txt` |

- Репозиторий меняется на мастере: `TELEMUX_STACK_TELEMT_REPO`, `TELEMUX_STACK_MTG_REPO`
  (например, на форк, когда у него появятся релизы в том же формате).
- Берётся последний релиз, не черновик и не pre-release (`/releases/latest`).
- `TELEMUX_GITHUB_TOKEN` - необязательный токен, только чтобы не упираться в лимит запросов.

### Проверка версий

- Мастер раз в 6 часов и по кнопке (`POST /api/v1/stack/check`, не чаще раза в минуту) узнаёт
  последний релиз каждого продукта. Результат - в таблице `stack_releases` (миграция 0013):
  продукт, репозиторий, версия, тег, дата, ошибка, время проверки. GitHub не ответил - остаётся
  прошлый результат и текст ошибки.
- Версии сравниваются по ядру `X.Y.Z` (ведущая `v` отбрасывается).
  - **Своя сборка** - версия на машине с суффиксом после ядра: `1.15.0-webalias`,
    `v1.12.0-15-g039ef04`.
  - **Доступно обновление** - ядро последнего релиза строго больше ядра на машине. Своя сборка
    `1.15.0-webalias` при релизе `1.15.0` обновлением не считается.
  - Версия, которую не удалось разобрать, - своя сборка, обновление не предлагается.

### Обновление машины

`POST /api/v1/machines/{code}/update {"product": "telemt" | "mtg", "version"?, "force"?}`:

1. Проверки:
   - машина включена, иначе 409 `machine_disabled`;
   - агент присылает этот продукт, иначе 409 `product_missing`;
   - на машине своя сборка - нужен `force`, иначе 409 `custom_build`;
   - версия не новее текущей - нужен `force`, иначе 409 `not_newer`;
   - обновление на машине ещё идёт (по любому продукту: одно обновление на машину за раз) -
     409 `update_in_progress`;
   - в релизе нет файла под архитектуру машины - 409 `asset_missing`.
2. Мастер скачивает архив релиза и проверяет SHA256 по контрольной сумме релиза, достаёт бинарь
   и кладёт его в кэш (`/var/lib/telemux/stack/<sha256 бинаря>`). Не скачалось или сумма не
   сошлась - 503 `release_unavailable` (в журнал мастера - причина). Загрузка - одна за раз,
   одинаковые запросы склеиваются, уже скачанный архив повторно не качается.
   - Подлинность релиза проверяется только контрольной суммой из того же релиза, без подписи.
3. Мастер публикует машине ресурс `stack`: JSON с одним обновляемым продуктом - версия,
   sha256 и размер бинаря. Ответ - 202 с номером ревизии.
   - `stack` - разовая команда, а не постоянное желаемое состояние: после итога (applied,
     failed, compare или 30 минут без отчёта агента) мастер той же транзакцией, что пишет
     итог, публикует новую ревизию без этого продукта (продуктов не осталось - `{}`). Иначе
     агент при перепроверке снова ставил бы бинарь поверх собранного вручную, а машина,
     вернувшаяся после долгого простоя, применила бы устаревшее обновление.
4. Агент (режим apply) видит, что версия на машине не та, и запускает вне своей песочницы
   `systemd-run --wait --collect telemux stack-apply --product <p> --sha256 <s> --version <v>`.
   - Агенту нельзя писать в `/usr/local/bin` (`ProtectSystem=strict`), поэтому замена бинаря -
     в отдельном процессе systemd.
   - `stack-apply` берёт бинарь у мастера (`GET /v1/stack/blobs/{sha256}`, токен агента, те же
     адреса и мосты, что у агента), сверяет sha256 и `--version`.
   - Дальше: копия `.bak`, атомарная замена, перезапуск сервиса (`telemt` или `mtg-multi`).
   - Проверка: сервис активен и API продукта отвечает в течение 30 с. Иначе - возврат `.bak`,
     перезапуск, код выхода 1.
5. Агент сообщает результат ревизии: `applied` или `failed` с причиной. Провал попадает в ленту
   тревог как `apply_failed` (ADR 0007).

В режиме compare агент только сообщает разницу («на машине X, нужно Y»).

### API

- `GET /api/v1/stack?limit=&offset=` - последние релизы и состояние по машинам: текущая версия,
  последняя, «доступно обновление», «своя сборка», последнее обновление и его статус.
- `POST /api/v1/stack/check` - проверить релизы сейчас (чаще раза в минуту - 429).
- `POST /api/v1/machines/{code}/update` - обновить продукт на машине.
- `GET /v1/stack/blobs/{sha256}` - бинарь для агента (токен агента; только бинари, которые мастер
  публиковал этой машине).

Запись - токен бота или вход в панель, только на мастере.

## Последствия

- Обновление telemt и mtg-multi - кнопка в панели, с проверкой суммы и откатом.
- Своя сборка mtg-multi защищена: обновить её можно только явно. Когда в форке появятся релизы
  в формате апстрима, достаточно сменить `TELEMUX_STACK_MTG_REPO`.
- Обновление самого агента telemux и xray сюда не входит.
