# ADR 0009. Релей - через свою зарубежную ноду

- Статус: принято (этапы 1-2 плана - telemux: мост, агент, мастер - сделаны)
- Дата: 2026-11-20
- Связано: [ADR 0001](0001-pull-reconcile.md) (мост), [ADR 0005](0005-servers.md) (серверы),
  [ADR 0007](0007-machines-ops.md) (тревоги)
- Спецификация: [specs/relay-via-exit.md](../specs/relay-via-exit.md), план:
  [plans/relay-via-exit.md](../plans/relay-via-exit.md)

## Контекст

- Связь зарубежная нода - релей в РФ односторонняя: релей сам поднимает обратный туннель к
  своей ноде, а с зарубежной ноды до релея прямой связи часто нет (так режет сеть, фаервол
  релея ни при чём).
- Внешние проверки (watchdog бота на ведущей ноде, аудит перед деплоем) ходили на релеи
  сами - по TCP и SSH с одной зарубежной ноды. Релей, который с неё не виден, считался
  мёртвым, хотя работал и отчитывался в telemux. Из-за этого живые релеи выводили из схемы.
- Две разные связи «релей - нода» живут отдельно:
  - туннель агента: `targets.relay_code` у выхода - через чей мост релей ходит к мастеру;
  - трафик: `servers.relay_code` + `servers.node_code` - какой релей держит сервер и какая
    нода у сервера выходом.

  Они разошлись: релей ходит к мастеру через ноды, которые к его серверам отношения не имеют.

## Решение

Цепочка одна: **мастер telemux -> зарубежная нода -> релей в РФ.**

- **Свои ноды релея** - выходы его серверов: `node_code` серверов с этим `relay_code`
  (плюс выход без серверов, если ему явно задан этот `relay_code`). Мост выхода обслуживает
  только свой релей: `targets.relay_code` выхода обязан совпадать с релеем его серверов,
  иначе `PUT /api/v1/targets/{code}` и `POST /api/v1/targets` - 400 `relay_mismatch`.
- **Релей ходит только к своим нодам.** Список мастеров агента релея (`agent.env`) строится
  только из своих нод - так уже устроен `relayExits`, меняются данные, а не код.
- **Мост знает свой релей.** Мост выхода помечает каждый запрос агента, который он пересылает
  мастеру, заголовком `X-Telemux-Bridge: <код выхода>` и запоминает, когда в последний раз
  через него ходил каждый релей (код берётся из ответа мастера на `/v1/desired`, токен
  проверяет мастер). Свою сводку мост отдаёт на loopback: `GET /v1/relays`.
- **Нода отвечает за свой релей.** Агент выхода раз в минуту читает `GET /v1/relays` своего
  моста и шлёт сводку в runtime-отчёте: код релея, когда релей был последний раз, сколько
  запросов через мост, были ли ошибки мастера.
- **Мастер спрашивает только ноду.** Статус пары считает мастер из отчётов выхода и
  заголовка моста:
  - `ok` - выход жив, и свежий отчёт релея пришёл через его мост;
  - `relay_silent` - выход жив, а релей через его мост молчит дольше порога (3 мин);
  - `exit_down` - сам выход молчит; о релее эта пара ничего не утверждает;
  - `foreign_bridge` - отчёт релея пришёл через мост чужой ноды (не из его пар).

  Релей считается упавшим, только если молчит через **все** свои ноды. Это видно в
  `GET /api/v1/pairs` и `GET /api/v1/machines` (`relay_via`, `relay_via_at`).
- **Тревоги** - в существующий детектор ADR 0007 (`machine_events`): `relay_silent` по паре,
  `relay_down` по релею, `foreign_bridge`. Лента `GET /api/v1/events` - единственный
  источник тревог о машинах; бот только пересылает её в Telegram.
- **Снаружи на релеи никто не ходит.** Watchdog и аудит бота состояние машин берут из
  telemux:
  - живость, `relay_silent`/`relay_down` - `events` и `pairs`;
  - диск, нагрузка - `runtime.host`;
  - клиенты - `runtime.telemt`;
  - применён ли конфиг и пользователи - `observed`;
  - ошибки telemt - `log-errors`.

  SSH- и TCP-проверки релеев с зарубежных нод для машин под telemux удаляются.
- **Проверки, которые нужно делать изнутри РФ** (выход релея в Telegram, профили TLS-эмуляции,
  мосты выходов `relay_exits`, доступность точек входа), делает агент самого релея как
  локальные проверки `checks` и отдаёт их тем же путём через мост. Это отдельный этап.

## Уточнения спецификации

Источник истины - [спецификация](../specs/relay-via-exit.md). Где она расходится с этим
решением, действует она:

- своя нода релея - только выход с `targets.relay_code` = релей (R5.1); проверки
  `relay_mismatch` с картой серверов нет;
- событие падения релея - `down` по правилу R3.3, отдельного `relay_down` в ленте нет
  (`relay_down` - поле пары).

## Этапы

1. telemux: заголовок и сводка моста, сводка в runtime-отчёте выхода, статус пары, тревоги,
   проверка `relay_mismatch`. Миграция: `agent_state.relay_via`, `relay_via_at`.
2. Данные: свести туннели и выходы релеев с фактическим трафиком, без дублей (через API, с
   «было -> станет»; до переключения проверить, что туннель на релее к нужной ноде поднят).
   Прод-топология - в приватной документации бота.
3. Бот: watchdog и аудит перед деплоем читают telemux вместо SSH/TCP на релеи; пересылка
   ленты событий в Telegram.
4. Агент релея: локальные проверки из РФ (выход в Telegram, TLS-эмуляция, мосты, точки
   входа).

## Отложено

- Резервный путь релея через вторую ноду - только если у релея несколько своих нод.
- Проверка доступности точек входа глазами клиентов из РФ (внешний сервис) - не часть
  telemux.
